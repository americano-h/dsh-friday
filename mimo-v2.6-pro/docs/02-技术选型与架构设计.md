# 02 · 技术选型与架构设计

> - 适用范围：dsh-friday（mimo-v2.6-pro 实现）的全部技术决策
> - 选型总原则：**优先复用 DSH 原生机制**（PRD 全界面原生、数据管理统一的要求），零第三方依赖，安装即用
> - 每项选型均给出「候选 → 结论 → 原因」；平台证据见 [03-平台可行性评估](03-平台可行性评估.md)

## 1. 总体架构：DSH 插件 bundle（Host + Client 双半）

> - 候选：① DSH 插件 bundle（cordis）② 独立 Web 应用 ③ 修改 DSH 源码内置
> - 结论：**① 插件 bundle**，Host 半（Node，业务与数据）+ Client 半（浏览器，UI）
> - 原因：
>   - PRD 要求侧栏入口、原生 UI、复用 harness/会话管理——只有插件形态能注册侧栏与浮层插槽
>   - 独立应用无法进入 DSH 侧栏与主题体系；改源码不可分发、不可多模型对照
>   - bundle 通过 `plugin_manager` 安装即生效，符合「完成灰度后随插件版本发布」的路线

## 2. 语言与构建：零依赖纯 JavaScript + 极简拼接构建

> - 候选：① TypeScript + tsdown 编译 ② 纯 ESM JavaScript（无构建）③ 纯 JS + 自研拼接器
> - 结论：**③ Host 纯 ESM；Client 源模块经 `scripts/build-client.mjs` 拼接为单文件 `client.js`（产物入库）**
> - 原因：
>   - 插件经 `link:` 本地安装时 npm 依赖解析不可靠（pnpm 对 link: 包不装依赖）；
>     本机并行开发的另一实现（零依赖）与官方模板同为零依赖路线，**不引入任何 npm 依赖**
>   - Client 半由 `window.__ModuleLoader__.load` 以工厂脚本装载，只能 `require` 平台模块表
>     （`react`、`react-dom`）；单文件拼接是官方模板同款形态，无编译器可用性风险
>   - TypeScript 可行（部署的构建工具能产出该格式）但引入工具链与产物漂移风险，
>     且本环境**不做安装验证**（用户决策），静态可验证性优先
>   - 拼接器只做「去掉 import/export 行后按依赖序拼接」的确定性变换，自身有单测兜底

## 3. Host↔Client 通信：围栏内 JSON 路由 + 原生 Remote 流

> - 候选：① `ctx.webServer.register` JSON 路由 ② `host.call`/`harness.handle` ③ 自定义 typert Remote
> - 结论：**① 插件私有 RPC 走 `/friday/api/*` 前缀路由；会话事件流走原生 `ctx.remote.session.*`**
> - 原因：
>   - `webServer` 路由是已验证模式（dsh-better-sidebar 的 `/sidebar/api`），用
>     `ctx.connection.requestRejection(req)` 围栏做鉴权，不自造信任判断
>   - `host.call` 的宿主侧 `harness.handle` 属动态包沙箱机制，对安装型 bundle 的适用性未经验证，不赌
>   - 会话的读/流/状态/搜索/标题均为稳定 Remote（`sessionController`），自己重写等于绕开框架
>   - 流式渲染订阅 `ctx.remote.session.observeEvent`（`agent/assistant-stream` 的持久化对应物），
>     不轮询、不扫全量日志

## 4. 会话与工具白名单：复用 `ctx.agents` + `tools.restrict`

> - 候选：① `ctx.sessions`/`ctx.agents` 创建会话 + 作用域工具限制 ② 自建轻量问答引擎（直接调 `ctx.llm`）
> - 结论：**①**；Inbox 会话就是 DSH Session，仅在创建与恢复时施加工具白名单
> - 原因：
>   - PRD FR-2.2 要求「存储与备份与 DSH 会话一致」，FR-1.7 要求崩溃不丢——复用会话日志天然满足
>   - `ctx.agents.create({ setup })` 的 `agentCtx` 作用域上 `tools.restrict({ allow: ['web_search'] })`
>     使 schema 展示、查找、执行三层一致地只暴露 web_search；再加 `tools.guard` 做无条件拒绝兜底
>   - 自建引擎需自持久化、自实现恢复/压缩/标题，重复造轮子且偏离「统一 DSH 机制」
>   - 标题生成直接用 `ctx.sessionTitle.refresh`（默认模型生成，FR-2.3/§8-13 原样满足）

## 5. 数据存储：插件私有 JSON 状态文件（元数据）+ DSH 会话日志（内容）

> - 候选：① `ctx.storageDomain`（域存储服务）② 会话事件携带元数据 ③ 插件私有 JSON 文件
> - 结论：**③ 元数据存 `<profileHome>/plugin-data/dsh-friday/state.json`（原子写）；问答内容只存会话日志**
> - 原因：
>   - 会话日志是唯一事实源（内容、图片、引用都不落插件存储）——只存会话自身无法表达的
>     插件侧状态：Inbox 成员、活动/归档态、升级目标、摘要索引、删除标记
>   - `storageDomain` 的 `DomainTableSpec.valueSchema` 要求 zod schema，与「零依赖」冲突；
>     且该服务为 DSH 内部域设计，插件跨版本契约不如文件直白
>   - 向会话追加自定义事件类型违反「未知事件类型」稳定性守则（practices 明确禁止）
>   - JSON 文件 + 原子写（临时文件 rename）+ 启动时校验与自愈，行为可测、可人工检修
>   - 位置选 `plugin-data/`（profile 下已有的插件数据目录），数据随 profile 走、与备份策略一致

## 6. 升级为正式任务：原生 `compaction` 服务 + `workspaceRegistry`

> - 候选：① `ctx.compaction.compactRegion` 原生压缩 ② 用默认模型自写「总结提示词」压缩
> - 结论：**①**，降级 ②（compaction 服务缺失或失败时）
> - 原因：
>   - FR-3.2 明确「压缩优先复用 DSH 原生能力」；`compactRegion` 返回 `CompactionResult.summary`
>     （内容块数组）即压缩后上下文，直接作新任务初始输入
>   - 新任务 = 新 DSH 会话 + `workspaceRegistry` 的 `attachSession` 挂入所选工作区 +
>     `uiWorkspace.openSession` 跳转，全链路原生；新建工作区复用 `uiWorkspace.pickDirectory` + `workspaces.create`
>   - 原会话归档态由元数据承载（`archived`），重复升级在服务端拒绝（FR-3.4）

## 7. 配置承载：`plugins.bundle.config` 配置页 + 插件私有状态

> - 候选：① 行级 `Config` schema + `configEditor`（写 cordis.patch.yml）② 自有配置页 + 私有存储
> - 结论：**②**，配置页注册在 `plugins.bundle.config`（键＝包名），读写走 `/friday/api/config`
> - 原因：
>   - PRD FR-4.1–4.3/4.5 要求四类配置集中在插件管理页；`plugins.bundle.config` 正是
>     「渲染在 bundle 页面上的自有配置区」的官方插槽
>   - 行级 `Config` 需 zod/schemastery 声明（零依赖冲突）；且 `configEditor` 编辑普通字段会
>     重启插件，模型/保留期的即时校验与下拉选择（来自 `modelCatalog`）需要自绘表单
>   - 配置存私有状态文件同址持久化，升级不丢；会在文档中声明偏离 practices 的「tunable 进 Config」
>     惯例及其原因（零依赖约束下的取舍）
>   - 快捷键绑定编辑不自造：配置页展示当前绑定并跳转 **DSH 原生快捷键设置**（`ctx.shortcuts` 设备级
>     持久化、冲突检测、平台差异处理全部原生获得），满足 FR-4.3「自定义」且符合 FR-4.4 原生 UI

## 8. 命名与共存（并行开发隔离）

> - 产品名：dsh-friday · Inbox；侧栏入口文案统一「Inbox」（FR-2.1/§8-7）
> - 包名 `dsh-friday`、行 id `dsh-friday`、模块 id 同包名；插槽 id：主面板/入口 `friday-inbox`，
>   浮层 `friday.quick-ask`，快捷键命令 `friday.quick-ask`
> - 用户决策：**安装延后**（不执行 `install_bundle`）。若与并行实现共存安装，改包名/行 id 为
>   `@mimo/dsh-friday` 即可双入口对照（README 有改名清单），互不覆盖

## 9. UI 实现守则（FR-4.4）

> - 只用主题 token（`--dsw-alias-*`）着色，字面色仅用于原创图标
> - 自绘控件（按钮/输入/列表/弹窗），不 `require('@deepseek-ai/dsh-client-ui-primitives')`（practices 禁止）
> - 组件内样式以 `<style>` 元素随组件挂载/卸载；类名统一 `fr-` 前缀，不与宿主冲突
> - 浮层挂 `shell.overlay`（框架级浮层，自带层级与点击穿透语义）；主面板占 `main` 插槽自有空间
> - Markdown 渲染自研（`src/shared/markdown.js`）：标题/粗斜/行内代码/代码块/列表/表格/引用/链接，
>   XSS 安全（全量转义后重建结构），LaTeX 不实现（延期）

## 10. 测试策略

> - 纯逻辑单测（`node --test`）：markdown 渲染、状态存储读写/迁移、保留期计算、升级状态机、拼接器
> - 静态验证：`node --check` 全部 JS、构建产物一致性、package.json/patch 结构检查
> - 运行时验收（安装后执行）：按 PRD §6 矩阵逐条人工/浏览器验证（见 docs/04）
